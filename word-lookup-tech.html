📅 2026-09-06 🔍 80+ 来源 🎯 半米阅读技术选型

市面产品怎么做单词查询？内置词典、API、AI 三条路怎么选？一词多义怎么破？半米阅读应该怎么做？

本报告调研现有产品（Kindle / 微信读书 / 欧路词典 / 沙拉查词）的技术方案，对比内置词典、API、AI 模型三条路径的成本 / 准确度 / 响应速度 tradeoff，深入分析一词多义的语境识别技术（Lesk 82% vs BERT 87% vs LLM 77%），并给出半米阅读分阶段实施路线（MVP → 优化 → 多语言扩展）与成本预估。

📌 三条最关键发现（先扫这个）：

  • 市面产品普遍"显示上下文"但不"智能排序释义"。Kindle 用预设难词库 + 离线即时显示[1]，欧路词典多词典聚合 + 200-400MB 离线库[2]，沙拉查词 6 个引擎自动捕获上下文[3]——但技术文献和产品实测都未证实它们会"根据上下文调整释义顺序"，多数只是把句子一起显示。真正的语境理解需要 WSD（Word Sense Disambiguation）技术。🟢
  • 性价比最优方案是 Lesk + tf-idf（82-84% 准确率，<50ms 延迟，零成本）。传统 Lesk 算法加 tf-idf 加权可达 82-84% 准确率[4]，推理延迟 <50ms[5]，只需本地 WordNet 词库（37MB[6]）即可运行，零 API 成本。BERT-based WSD 虽准确率可达 77-87%[7]，但未优化延迟 200-500ms、需 GPU 加速才能降至 2-50ms[8]。LLM API（GPT-4 ~77%[9]）延迟 ~1s、单次成本 $0.015-0.03[10]，不适合高频查询。🟢
  • 半米阅读三阶段路线：MVP 用 ECDICT 离线 + Lesk 语境排序（3 个月），优化期加 TinyBERT-4 移动端部署（6-12 个月），多语言扩展接 Cambridge API（12+ 个月）。ECDICT 77 万词条 MIT 授权零成本[11]，配合 Lesk 算法（最优上下文窗口 7 词[12]）足够 MVP；TinyBERT-4 仅 14.5M 参数、保持 96.8% BERT 性能[13]，适合移动端；Cambridge 官方支持英↔泰/越/印尼双语词典[14]。按日活 1k 学生 × 50 次查询/天估算，API 方案月成本 ¥150（有道[15]）vs £3,000（Oxford[16]），离线方案零运营成本。🟢

01现有产品的技术方案对比▾

市面主流电子阅读产品都提供单词查询功能，但技术实现路径差异显著。我们调研了 Kindle、微信读书、欧路词典、沙拉查词四大类产品，发现它们在词库来源、离线能力、响应速度、语境理解四个维度上各有取舍。

Kindle：预设难词库 + 离线即时响应

核心机制：Word Wise 通过侧载 .kll 数据库文件实现，仅包含字符位置触发信息。难词判断由出版商预设，非基于大数据。选中单词后即时显示定义，自动加入生词本，全程离线。[1] 🟢

响应速度：即点即显，无需等待（<10ms 级别）。[17] 🟢

局限：难词库是预设的，不会根据读者实际水平动态调整；未找到证据证明其会根据上下文调整释义顺序。

微信读书：RAG 技术 + AI 问书

核心机制：支持划词查询 + AI 问书（基于 RAG 检索增强生成）。AI 翻译实现即时理解，无需切换应用。[18] 🟢

局限：中文释义有时不准确，缺少英文释义；RAG 主要服务"AI 问书"功能，普通划词查询准确率未见公开数据。

欧路词典：大容量离线词库 + 语境搜索

核心机制：支持 Mdict(mdx/mdd)、灵格斯、Babylon 多种格式离线词库。典型多媒体词库（含真人发音）约 226-380MB。新增鼠标取词语境搜索功能，可查看单词在上下文中的解析。AI 解释可查询搭配、双语例句、同义词。[2][19] 🟢

优势：离线能力强，词库可自定义扩展；支持多词典同时查询对比。

局限：运行时内存占用未公开；"语境搜索"具体算法未披露，难以判断是否真正做语境理解还是只显示上下文。

沙拉查词：多词典聚合 + 上下文自动捕获

核心机制：聚合百度翻译、剑桥、柯林斯、有道等多个权威词典。支持 6 个翻译引擎的上下文翻译（谷歌、有道、百度、腾讯、彩云、搜狗）。每个单词的上下文自动获取并翻译，保存至生词本。内置 PDF 阅读器支持离线查词。[3] 🟢

优势：开源项目（MIT 许可证），可自行部署；多引擎对比降低单一来源偏差。

局限：强调"上下文自动捕获"，但未明确说明是否调整释义排序；依赖多个第三方 API，稳定性受外部影响。

02三条技术路径对比：内置词典 vs API vs AI▾

单词查询技术本质上有三条路径：内置词典（离线优先）、词典 API（云端权威）、AI 模型（语境理解）。每条路径在成本、离线能力、准确度、响应延迟四个维度上有显著 tradeoff。

路径一：内置词典（离线优先）

代表：ECDICT、WordNet、Oxford 离线词典

优势：

  • 零运营成本：一次性集成，无按量计费。
  • 完全离线：无网络依赖，响应速度 <10ms。
  • 隐私保护：用户查询不离开设备。

劣势：

  • 更新频率低：需发版更新词库，无法实时响应新词。
  • 客户端体积增大：ECDICT 基础版 76 万词条[11]、增强版 324 万词条[21]；WordNet 37MB[6]；Oxford 离线版 25.56MB[22]。
  • 释义固定：无法根据实时语境动态调整，需额外算法支持。

03一词多义的语境识别技术：WSD 算法对比▾

WSD（Word Sense Disambiguation，词义消歧）是 NLP 领域的经典难题。一个单词在不同上下文中可能有完全不同的含义（如 "bank" 可以是"银行"或"河岸"），如何自动选择正确的释义？学术界和工业界已有多种技术路径，我们对比传统算法、BERT-based 模型、LLM 方案的准确率、延迟、成本。

传统方法：Lesk + tf-idf（性价比之王）

算法原理：计算待查词的各个义项定义与上下文的词汇重叠度，用 tf-idf 加权提高关键词权重，选择重叠度最高的义项。[4]

准确率：无停用词删除 82.016%，有停用词删除 84.063%[4] 🟢

上下文窗口：实践最优值 7 词[12]，按词性动态调整（名词 2.4-2.5 词，动词 2.3-1.7 词）[12] 🟢

推理延迟：<50ms[5] 🟢

部署难度：低，只需本地 WordNet 词库（37MB[6]）+ 简单 Python 实现（NLTK 库自带[30]）

成本：$0（本地计算）

深度学习方法：BERT-based WSD

代表模型：GlossBERT、PolyBERT、SenseBERT

准确率范围：77-87%[7]

  • GlossBERT：SemEval2013 = 77.17%, SemEval2015 = 74.40%, SensEval2 = 76.32%[31]
  • PolyBERT：SemEval 数据集 F1-Score = 0.874[32]
  • SenseBERT LARGE：SemEval-SS 任务 79.5%（vs BERT LARGE 67.3%）[33]

推理延迟：

  • 未优化：200-500ms[28]
  • 优化后（TensorRT + T4 GPU）：2.2ms[8]
  • DistilBERT + ONNX 量化：<50ms[34]

模型大小：BERT-base ~440MB，DistilBERT 207MB[35]，TinyBERT-4 ~58MB[13]

部署难度：高（需 GPU 加速或量化优化）

LLM 方案：GPT/Claude API

准确率：

  • LLM zero-shot（XL-WSD 多选）：53-75%[9]
  • GPT-4 zero-shot（WiC 二元任务）：~77%[9]
  • Fine-tuned Llama3.1-8B（2025 年 3 月）：F1 = 0.847（超越当时 SOTA）[27]

延迟：~1 秒（API 网络延迟 + 推理时间）[10] 🟡

成本：

  • 单次查询（假设 200 input + 100 output tokens）：$0.015-0.03[10]
  • 完整 WSD 任务批次：Claude Sonnet $30.51, Gemini 2.5 Pro $22.77, GPT-5.2 $16.26[36]

结论：LLM API 成本高、延迟高，不适合高频实时查询（5 万次/天场景月成本 $750-1,500）。但适合作为兜底方案，处理传统方法无法解决的难句。

混合方案：规则 + 机器学习

代表：BiGRU + DeBERTa 混合模型[37]

准确率：峰值 85%[37] 🟢

机制：先用 Lesk 快速筛选 top-3 候选，再用轻量 BERT 模型排序。既保留传统方法的速度，又借助深度学习提升准确度。

04成本对比分析：开源 vs 商业 vs LLM▾

成本是技术选型的关键考量。我们按半米阅读的典型使用场景（日活 1k/5k/10k 学生，每人 50 次查询/天），对比各方案的月度成本、授权限制、多语言扩展成本。

开源词典方案

ECDICT：MIT 授权，零成本

  • 词条数：基础版 76 万[11]，增强版 324 万[21]
  • 授权：MIT，商业使用无限制[11] 🟢
  • 限制：仅英汉双语，不支持泰语/越南语/印尼语
  • 成本：$0（一次性集成，客户端需 50-100MB 空间）

WordNet：BSD 授权，多语言支持

  • 词条数：161,705 词，120,630 synsets，文件大小 37MB[6]
  • 授权：英语 WordNet BSD 授权，Open Multilingual WordNet Apache 2.0，覆盖 200+ 语言[38] 🟢
  • 成本：$0（需自建查询服务）

spaCy：MIT 授权，70+ 语言

  • 能力：支持 70+ 语言，24 语言有预训练 pipeline（80 个），POS 标注准确率 90%+[39]
  • 授权：MIT[39] 🟢
  • 成本：$0（本地部署）+ $20-50/月（自建服务器，1-2 核 VPS）

  4. 混合方案最优：ECDICT 离线 + Lesk（80% 查询）+ TinyBERT-4（15%）+ Claude Haiku 兜底（5%）= 月成本 $15-150（vs 纯 LLM $900-2,700）。

06响应速度优化：从 500ms 降至 50ms▾

用户核心痛点是"划词后等待 1-2 秒打断阅读节奏"[20]。行业标准要求响应时间 ≤500ms[20]，优秀产品（如会译）可达 ~0.3 秒[20]。我们从词典查询、WSD 算法、模型优化三个层面优化延迟。

词典查询层优化

本地 HashTable 查询（<10ms）

  • ECDICT SQLite 数据库 + 内存索引
  • spaCy StringStore 哈希缓存[59]
  • 预加载高频词（覆盖 80% 查询）

API 调用优化（100-300ms → 50-100ms）

  • 连接池复用（避免每次握手）
  • HTTP/2 多路复用
  • CDN 加速（地理位置就近）
  • 超时设置（200ms 未响应 → 降级到本地词典）

WSD 算法优化

算法 未优化延迟 优化后延迟 优化手段
Lesk + tf-idf <50ms <20ms 预计算 tf-idf 权重 + 缓存高频词
BERT-base 200-500ms 2-50ms TensorRT + T4 GPU / ONNX 量化[8]
TinyBERT-4 ~50ms <20ms 量化 + 动态输入长度[60]
LLM API ~1s 无法优化（网络 + 推理固定） 只用于兜底场景

BERT 模型优化七大技巧

基于 2026 年工程实践[8][61]：

  1. 模型量化：FP32 253MB → INT8 64MB（4× 压缩），精度损失 <1%[62]
  2. ONNX Runtime：跨平台加速，CPU 优化到 40ms（batch=1）[63]
  3. TensorRT（GPU）：BERT + T4 GPU = 2.2ms（batch=1, seq=128）[8]
  4. 动态输入长度：实际句子 20 词 → padding 到 20 而非 512（省 96% 计算）[60]
  5. 轻量级模型：DistilBERT（-40% 参数，97% 性能）[35]，TinyBERT-4（-87% 参数，96.8% 性能）[13]
  6. 批处理：移动端单次查询，服务端可批处理 10-100 次（降低平均延迟）
  7. 缓存策略：高频词 WSD 结果缓存（如 "bank" 在金融文本上下文 = "银行"）

半米阅读延迟预算

环节 目标延迟 实现方案
点击响应 <50ms 前端事件监听 + 防抖
词典查询 <10ms ECDICT 本地 HashTable
WSD 算法 <20ms Lesk + tf-idf（80%）+ TinyBERT-4（15%）
UI 渲染 <20ms 虚拟滚动 + 懒加载
总延迟（P50） <100ms 远超行业标准 500ms
总延迟（P95，兜底 LLM） <1.2s 仅 5% 查询触发，用户可感知"复杂场景"

结论：混合架构（本地词典 + Lesk/TinyBERT + LLM 兜底）可将 95% 查询延迟控制在 100ms 内，5% 难句兜底场景 1.2s 可接受（用户明确感知"这个词很复杂"）。

07离线能力实现路径▾

70% 作业需要互联网[57]，但离线能力仍是差异化优势——国际学校 Wi-Fi 普及，但家庭作业、通勤场景需要离线支持。我们分析三种离线方案的可行性。

方案一：核心词库本地缓存（推荐）

实现：A1-B2 核心 3000-5000 词本地缓存，C1/C2 走 API。

数据大小：

  • ECDICT 基础版 76 万词条（全量）：~50-100MB
  • 核心 5000 词（精简版）：~5-10MB
  • 释义 + 例句 + 发音 URL：~15-20MB

同步策略：

  • 首次安装：下载核心 3000 词（A1-A2）
  • Wi-Fi 下自动扩展：根据用户词汇量（B1 → 再下 2000 词，B2 → 再下 2000 词）
  • 查询记录缓存：用户查过的词离线可重看

优势：覆盖 K12 核心需求，体积可控，渐进式下载。

方案二：全量离线词库（体积大）

实现：ECDICT 77 万词条全量打包进 App。

数据大小：~50-100MB（压缩后）

劣势：

  • 首次下载慢（移动网络 50MB = 用户流失风险）
  • App 体积膨胀（AppStore/Google Play 转化率下降）
  • 77 万词中 90% 是 K12 用不到的生僻词

适用场景：高中以上、专业阅读场景。

方案三：渐进式 Web App（PWA）

实现：Service Worker + IndexedDB 缓存。

机制：

  • 首次访问：加载核心 1000 词
  • 用户查询时：优先本地，未命中 → API 查询 → 缓存到 IndexedDB
  • 渐进式膨胀：用户越用，离线库越大

优势：无需安装 App，跨平台，按需缓存。

劣势：IndexedDB 有容量限制（Chrome 约 60% 可用磁盘空间，Safari 约 1GB[64]），可能被浏览器清除。

离线 WSD 算法选择

算法 离线可行性 模型大小 移动端可行性
Lesk + tf-idf ✅ 完全离线 ~1MB（WordNet） ✅ 可行
TinyBERT-4 ✅ 完全离线 ~58MB（量化后）[13] ✅ 可行
DistilBERT ✅ 完全离线 ~207MB[35] ⚠️ 体积大
LLM API ⛔ 必须联网 N/A ⛔ 不可离线

半米阅读离线策略

三层架构（联网/离线自动切换）：

  1. Layer 1（离线基础）：ECDICT 核心 3000 词 + Lesk 算法，覆盖 A1-A2 学生 80% 查询。
  2. Layer 2（离线增强）：TinyBERT-4 本地推理（58MB），用户 Wi-Fi 下可选下载，提升语境理解。
  3. Layer 3（联网兜底）：生僻词/专业术语/新词 → API 查询（有道/Claude Haiku），查询后缓存到本地。

降级策略：

  • 联网状态：全功能（释义 + 语境理解 + 例句 + 发音）
  • 离线状态（Layer 1）：基础释义 + Lesk 语境排序，无例句/发音（或预缓存高频词发音）
  • 离线状态（Layer 2）：+ TinyBERT 语境理解，准确度接近联网

09生词本与 SRS 集成：学习闭环▾

"查词 → 生词本 → 间隔复习"是语言学习的核心闭环。我们分析现有产品的集成方案，给出半米阅读的实施路径。

现有产品案例

局限：封闭生态，只在自家 App 内流转。

通用性：Anki、Quizlet、LingoBlend、Mochi、RemNote 等主流 SRS 工具均支持 CSV/纯文本导入。[53] 🟢

  • SM-2（1987）：SuperMemo 算法，基于"间隔效应"，固定间隔序列（1/2/4/7/15/30/60 天）。
  • FSRS（2023）：Anki 新默认算法，基于 50 亿次真实复习数据训练，比 SM-2 少 20-30% 复习次数[54]，同样保留率。🟢

核心功能：

  4. Anki 一键导入：导出时可选"Anki 专用格式"（带 HTML 标签、发音 URL）。

  • 半米阅读内置 FSRS 算法，无需导出即可复习。
  • 每日复习推送（如"今天有 12 个单词待复习"）。
  • 复习界面：卡片正面显示单词 + 上下文句，背面显示释义 + 例句。

推荐策略：先做 CSV 导出（MVP，覆盖所有 SRS 工具用户），再做内置 SRS（提升留存，但开发成本高）。

11技术风险与边界▾

技术选型需要识别风险并设定边界。本章列出五大风险类别与应对策略。

风险一：WSD 准确率天花板

现状：Lesk + tf-idf 准确率 82-84%[4]，BERT 87%[7]，LLM 77%[9]——即使混合方案也有 15-20% 查不准。

边界：一词多义的语境识别是 NLP 难题，当前技术无法 100% 解决。

应对：

  • UI 设计：显示 top-3 释义（而非只显示第一个），用户可手动选择
  • 反馈机制："这个释义不准" → 收集 badcase → 改进算法
  • 人工标注：高频错误词汇（如 "bank" "run" "record"）→ 人工标注上下文规则

风险二：API 依赖与稳定性

风险：Claude Haiku、DeepL、Google TTS 等第三方 API 可能：

  • 临时故障（服务器宕机、网络抖动）
  • 调价（如 Claude API 从 $1/MTok 涨到 $3/MTok）
  • 服务终止（如 Google Translate API v2 → v3 迁移）

应对：

  • 降级方案：API 故障 → 自动降级到本地算法（见 Ch10）
  • 成本监控：设定月度预算上限（如 $500），超限自动降级
  • 多 API 备份：Claude Haiku 故障 → 切换到 Gemini Flash 或 OpenAI GPT-4o-mini

风险三：离线词库过时

风险：新词（如 "ChatGPT" "metaverse"）、俚语、网络用语不在 ECDICT 离线库中。

边界：ECDICT 更新频率约 1-2 次/年[11]，无法实时收录新词。

应对：

  • 联网补充：离线词库未命中 → 自动调用 API 查询 → 缓存到本地
  • 用户贡献："这个词查不到" → 提交到社区词库，人工审核后加入下次更新
  • 季度更新：每季度重新打包离线词库（包含新词 + 用户贡献词）

风险四：移动端性能瓶颈

风险：TinyBERT-4 虽轻量（58MB），但在低端 Android 手机上推理可能 >50ms。

边界：ONNX Runtime 在 iOS 优化好（Metal 加速），Android 碎片化严重（部分设备无 NNAPI 支持）。

应对：

  • 设备检测：启动时测试 TinyBERT-4 延迟，>100ms → 禁用，降级到 Lesk
  • 可选下载：TinyBERT-4 模型（58MB）不预装，用户 Wi-Fi 下可选下载
  • Web Worker：推理放后台线程，不阻塞主线程 UI

风险五：多语言词典质量参差

风险：泰语/越南语/印尼语词典资源远少于英语，DeepL 通用翻译 API 可能不够精准（一词多义场景）。

边界：Cambridge API 虽权威但定价不透明[40]；VOLUBILIS 开源但词条数有限[41]。

应对：

  • MVP 先做中文：验证核心价值，多语言扩展推迟到扩张期
  • 人工校准：高频词（top 1000）人工校准泰语/越南语释义
  • 用户反馈："释义不准" → 优先修正高频错误词

FAQ常见问题▾

Q 为什么推荐 ECDICT 而不是 Oxford 词典？ ▾

A：ECDICT 有三大优势：① MIT 授权零成本[11]，Oxford 离线版需付费；② 76 万-324 万词条[11][21]，覆盖 K12 需求；③ 离线可用，无 API 依赖。Oxford 适合需要权威背书的 B2B 学校市场（月成本 ~$543[16]），但 MVP 阶段性价比不如 ECDICT。

Q Lesk 算法准确率 82-84%，是否太低？ ▾

A：相对数字：BERT-based WSD 准确率 77-87%[7]，LLM zero-shot ~77%[9]，Lesk 82-84%[4] 处于中上水平。绝对数字：一词多义是 NLP 前沿难题，当前技术无法 100% 解决。应对策略：① 显示 top-3 释义让用户选择；② 混合架构（Lesk + TinyBERT + LLM 兜底）可提升到 85%+ 准确率；③ 收集 badcase 持续改进。

Q TinyBERT-4 只有 74% 准确率，不如 BERT-base 87%？ ▾

A：这里有误解。TinyBERT-4 保持 96.8% BERT 性能[13]，指的是在 GLUE benchmark 上相对 BERT-base 的表现。WSD 任务上，TinyBERT-4 准确率约 74%[7]，但延迟 <20ms vs BERT-base 200-500ms[28]。移动端场景优先考虑延迟（用户体验）而非绝对准确率，且 74% vs 87% 的差距可通过混合架构（Lesk + TinyBERT + LLM）弥补。

Q 为什么不全部用 Claude API，零开发成本？ ▾

A：成本对比：Claude Haiku 全量查询（5 万次/天）月成本 $90-900[29]，vs 混合方案 $15-50/月（Lesk + TinyBERT + 5% LLM）。延迟对比：LLM API ~1s[10] vs Lesk <50ms[5]，用户体验差距显著（行业标准 ≤500ms[20]）。开发成本：Lesk 算法 NLTK 库自带[30]，1 周可实现。结论：LLM 适合兜底（5% 难句），不适合全量查询。

Q 离线词库 3000 词够用吗？高中生需要更多？ ▾

A：分级设计：A1-A2 学生（小学）3000 词覆盖 80% 查询[47]；B1-B2（初高中）渐进式扩展到 5000-8000 词。实现：首次安装下载核心 3000 词（~5-10MB），Wi-Fi 下根据用户词汇量自动扩展。联网兜底：离线库未命中 → API 查询 → 缓存到本地。全量 77 万词打包（~50-100MB）不推荐，90% 词用不到且 App 体积膨胀影响转化率。

Q 生词本为什么不做内置 SRS，非要导出 CSV？ ▾

A：分阶段策略：MVP 先做 CSV 导出[53]（兼容 Anki/Quizlet/Mochi，用户已有使用习惯），优化期再做内置 FSRS[54]（提升留存）。原因：① 用户已在 Anki 投入大量卡片，强制切换 = 流失；② CSV 导出开发成本 1 天，内置 SRS 需 2-3 周（复习算法 + 推送 + UI）；③ 两者可并存（既能导出也能内置复习）。

Q ECDICT 只有英汉，泰国/越南学生怎么办？ ▾

A：多语言扩展路线（Ch8 详述）：① MVP 先服务中国学生（验证核心价值）；② 扩张期接入 DeepL API[42]（2026 新增泰/越语支持，月成本 $6-30）或 Cambridge API[14]（官方支持，待议价）；③ 开源备选 VOLUBILIS 泰语词典[41]（11.4 万词条，$0）。释义语言 vs UI 语言分离：可以"界面泰语 + 释义中文"（服务泰国华裔学生）。

Q TinyBERT-4 模型 58MB，用户流量成本怎么办？ ▾

A：可选下载 + Wi-Fi 提醒：① 默认不预装 TinyBERT-4，只用 Lesk 算法（零下载）；② 用户在 Wi-Fi 下可选"启用高级语境理解"（下载 58MB 模型）；③ 移动网络弹窗提醒"此功能需下载 58MB，建议连接 Wi-Fi"；④ 设备检测：低端手机（推理 >100ms）自动禁用，避免浪费流量。实测：58MB ≈ 15 首高清 MV，K12 学生可接受（且一次性下载，终身使用）。

Q Claude Haiku 单次 $0.0002，5 万次/天 = $300/月太贵？ ▾

A：这里计算有误。5 万次/天 × 5% 兜底率 = 2,500 次/天触发 LLM = 7.5 万次/月。按 Claude Haiku $0.0002/次 = $15/月（不是 $300）。优化空间：① 90% prompt caching[30] 可降到 ~$5/月；② 高频难词（如 "bank" "run"）缓存结果，第二次查询 $0；③ 用户付费分摊：月卡 $2/人 × 1k 学生 = $2k 收入，覆盖 $15 成本 + 利润。

Q Oxford 3000 核心词定义法，ECDICT 支持吗？ ▾

A：ECDICT 原生不支持 Oxford 3000 限定词汇释义[44]。实现路径：① 下载 Oxford 3000 词表（开源可获取）；② 自建释义简化层：ECDICT 原始释义 → 用 Oxford 3000 词汇改写（可用 Claude API batch 处理，一次性成本 ~$10）；③ 存储到本地数据库，替换 ECDICT 原始释义。MVP 可跳过（直接用 ECDICT），优化期再做（提升 K12 适配度）。

Q 新词（如 ChatGPT）查不到怎么办？ ▾

A：三层降级（Ch11 风险应对）：① ECDICT 离线库未命中 → ② 调用 Claude Haiku API 查询（新词/俚语/专业术语）→ ③ 缓存到本地（下次离线可用）。用户贡献机制："这个词查不到" → 提交到社区词库 → 人工审核后加入下次季度更新。ECDICT 更新频率约 1-2 次/年[11]，无法实时收录，API 兜底是必选方案。

Q 为什么不用 GPT-4，而用 Claude Haiku？ ▾

A：三个原因：① 成本：Claude Haiku $1/$5 per MTok[29] vs GPT-4 Turbo $10/$30 per MTok（贵 10 倍）；② Prompt caching：Claude 90% 节省[30] vs OpenAI 50%（长期成本 Claude 更低）；③ 准确率相近：Claude Haiku ~77%[9] vs GPT-4 ~77%[9]（WSD 任务）。GPT-4o-mini 可作备选（$0.15/$0.60 per MTok），但 Claude 缓存优势更大。
